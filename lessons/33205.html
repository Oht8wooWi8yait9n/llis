NASA Lesson #33205: Mitigating Possible Software Errors During Reentry of Crewed Spacecraft

Lesson ID: #33205 (Database ID: 33205)
Date: 2020-12-11
Organization: nesc
Program Phase: Implementation &raquo; Phase D
Topic / Category: Software, Spacecraft, Entry Systems, DDT/E, Level 0/1 Requirements, Early requirements and standards definition, Reliability
Source: View Official NASA LLIS Entry (live system)

Driving Event / Description

The NESC assessed contingency and backup operations for historical crewed spacecraft during reentry. Several American and Russian crewed spacecraft had backup methods to ensure safe reentries that did not rely on common software computer control. These methods were possible because of the inherent stability and controllability of the spacecraft. However, if a vehicle is unstable transonically and cannot initiate or continue a safe reentry without active computer control, or there are skewed RCS thrusters requiring algorithmic logic to perform uncoupled rotations about individual axes, or there is no provision for manual control, reentry can be difficult, if not impossible, to recover from common mode software or hardware flight computer failures during this critical time.

Lesson(s) Learned

Spacecraft aerodynamic instability and reaction thruster off-axis skewing greatly reduce contingency or backup options for safe return of crew in the event of a single common flight control computer failure. Inherently unstable spacecraft configurations, skewed thruster configurations, and lack of manual controls and displays require reliance on-board flight control computers which bring the inherent risk of common software failure that makes a successful, uncontrolled reentry unlikely.

Recommendation(s)

NASA should explicitly express a preference for stable designs that enable greater robustness and to not require computer control to safely return crew to Earth. A stable spacecraft can allow manual or non-controlled reentry options that can save the lives of the crew. NASA should avoid unstable designs that require working compute elements and software with no errors. If such a design is necessary, this additional computer risk should be considered.
